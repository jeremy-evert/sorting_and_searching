# Sins: grievances about this repository

A Festivus airing, written on 2026-11-09. These are observations and judgments, not a list of accepted defects. Some repeat `TASKS.md`: they are here because they bother me, not because they have been independently resolved. This is a snapshot, not a verdict on the people or agents who built the work.

## The story we tell

- **The front door is behind the project.** `README.md` says the plots and home page are in progress, although they are present. A showcase should know its own state and give a visitor a direct route to the interesting results and to running the project.
- **The theory is simplified past the point of being quite true.** `BIG_O.md` says Big O is a statement about a doubling ratio. Big O is an asymptotic upper bound; a measured ratio at two sizes can illustrate a growth pattern, but it cannot establish one. The page also presents the two input-sensitive cases as exceptions, though its predictions already account for them.
- **We sound more certain about random quicksort than the evidence allows.** `BIG_O.md` says the observed difference comes from two causes, while `TASKS.md` explicitly says the explanation needs more trials. Five trials and two sizes are a thin basis for attributing the discrepancy.
- **The checkers oversell their reach.** `check_big_o.py` prints that every quoted number matches, but checks the marked tables, not the surrounding prose. `check_site.py` checks structure and local file existence, not whether alt text accurately describes the image, external links work, or the page reads well. Green output can give a stronger impression than the checks deserve.
- **The build record is harder to trust than it needs to be.** `LEDGER.md` leaves prompt 06 open; its report says FAILED, while its branch was merged. Prompt 07 has a report but remains in the open prompts folder and has no ledger row. The README for the record promises a cleaner trail than a new reader actually finds.

## The pictures

- **The search graph uses the wrong reference for the story we are telling.** `plotter.py` draws `n/2`, while half the searches miss and `BIG_O.md` explains that the mixed workload averages roughly `3n/4`. Without context, the reference invites a reader to infer a discrepancy that the workload itself explains.
- **Important curves hide each other.** Bubble and selection have the same comparison counts; both binary searches have the same probe counts. The plots use different markers, but the overlapping series still make comparison harder. The project already knows this and has not settled how to present it.
- **One alt description describes a curve that is not there.** The quicksort image in `docs/index.html` says it includes an `n log n` curve, but `plot_big_o` draws the measured points and one fitted prediction, `n squared` for sorted quicksort. A screen-reader user gets a different picture from a sighted reader.
- **The class diagram asks a phone reader to pan.** The page sets a 560-pixel minimum width and scrolls the diagram inside a box. It is a lot of detail before a newcomer has a simple map of the system.
- **Perceived grievance:** the site leads with small side-by-side graphs and a class diagram, but I have not done a fresh visual or accessibility review. I suspect the strongest story could be clearer and more legible, especially on a phone; that needs a real review, not a claim that it fails.

## The evidence and the code

- **Reproducing the whole exhibit is not a single obvious action.** The experiment and plotting scripts exist, but the README does not take a reader through generating both CSVs and images, and there is no automated check that fresh results match the committed ones. The original hash checks are historical evidence, not a continuous guard.
- **There is no visible automated test matrix.** The project promises Python 3.9 and newer, but there is no committed CI workflow showing supported versions being tested. During this inspection, `python -m pytest -q` produced 74 passed and 8 setup errors because pytest could not create its temporary directory in this environment; that is not evidence of an algorithm failure, nor a full passing run.
- **The design has drifted from its implementation.** `sidecar/DESIGN.md` gives a different `Plotter` interface from the one in `src/sortsearch/plotter.py` and omits `results_io.py` from its layout. It calls itself the truth, so these mismatches matter.
- **The counting rules are easy to misunderstand.** Search comparisons count one three-way decision per probe; sort moves exclude merge's final copy back; sorting's final validation is not counted. These are legitimate conventions, but generic labels like â€œcomparisonsâ€ and â€œmovesâ€ can look like counts of every underlying operation. The definitions need to travel with the conclusions.
- **The sorter checks order, not preservation.** `Sorter.sort` rejects an unsorted output, but a broken child that discards or duplicates values could still return a sorted list. Tests check expected output for actual sorters, so this is a limitation of the base-class guarantee, not proof that a current sorter loses data.
- **The â€œno globalsâ€ rule and the code do not agree literally.** The manager and plotter have module-level constants. They are configuration and labels rather than mutable experiment state, but the rule should say that if that is what it means.
- **Perceived grievance:** the inheritance hierarchy may be teaching the requested class structure more than it is simplifying the algorithms. `RecursiveSearcher` and `RecursiveSorter` deserve a beginner-focused review of what each abstraction actually earns; this is a design question, not a demand to flatten them.

## Public polish

- **The published record needs a deliberate privacy review.** `questions/07_history_identity.md` identifies author identity in existing history, and `TASKS.md` records a pending metadata sweep of PDFs and images. The current observation is a known open question, not a claim that every artifact is unsafe. A mailmap can change display; it does not erase historical identities.
- **The root-level field guide is unexplained at the front door.** `Deciding_with_AI_Field_Guide_print.pdf` is prominent in the file list, but the README does not explain its relationship to this project.
- **Perceived grievance:** the formal PDF has not been proofread according to `TASKS.md`, and I have not independently read it for this pass. I would not call the final document polished until someone does.

These grievances are not automatically a work order. Verify the perceived ones, choose the fixes that best serve the showcase, and keep the useful history even when it is messy.

## What mattered

These are the choices and findings that changed the design or the numbers. Each is worth keeping when the code is reworked.

- **Count operations, never seconds.** Every claim in the repo is an exact count from a fixed seed, so any result can be reproduced and any number can be checked. Prompt 02 proved it by hashing the CSVs from two runs.
- **Hand-worked tests.** The expected values were derived from the algorithm (for example `[3, 1, 2]` gives bubble 3 comparisons and 4 moves) and written as a comment before the assertion. The code matched on the first run, which is the point of doing it that way (01, 02).
- **Check numbers with a script, not by eye.** `check_big_o.py` fails if a table in `BIG_O.md` drifts from the data; `check_site.py` fails on a broken link or a missing section. Both caught real problems when tested with a deliberately wrong input (04, 05).
- **Quick sort with a first-element pivot is deliberately quadratic on sorted input.** `max_depth` is exactly 100 for n=100 and the comparisons equal bubble sort's (204480 at n=640). This is the clearest demonstration of why Big O depends on input (01, 04).
- **Linear search averages 3n/4, not n/2.** Half the lookups hit (about n/2) and half miss (n). The prompt's expectation was wrong and the data corrected it (04).
- **Binary search sits about 0.45 probes under log2 n** because hits are found before the last halving (04).
- **Insertion sort on sorted input is linear**, because each insert is one comparison and one move (04).
- **Honest reporting found things.** The overlapping bubble and selection lines (03, 05), the first screenshots that cut the page off (05), and the prose number written as 2.2 then corrected to the measured 2.31 (04) all came from reports that listed gaps instead of hiding them.

## Working habits that paid off

- Each prompt states why, constraints, and an acceptance test that can fail. Reports answer the acceptance items one by one.
- One branch, one worktree, one report per prompt; the reviewer merges.
- A fresh clone to run the tests, so a missing file or path cannot hide (01, 03).
- Stage files by name, so scratch output does not get committed.

===== sidecar/DESIGN.md =====
# Design: sorting_and_searching

A small, public codebase that does two jobs at once:

1. **Measure** how sorting and searching algorithms behave as the input grows, and show that the measurements match Big O predictions.
2. **Demonstrate good code**: well-formed classes, clean inheritance, readable names, one clear design.

It is a display piece. The code is built to be read, so every choice below favors clarity over cleverness.

## What it counts (and why not time)

Algorithms report **operations**, not seconds. A `Counter` object is passed into every algorithm and records:

| field         | meaning                                          |
|---------------|--------------------------------------------------|
| `comparisons` | times two values were compared                   |
| `moves`       | times a value was written to a new position (a swap counts as 2 moves) |
| `probes`      | times a search looked at one element             |
| `max_depth`   | deepest recursion reached (0 for non-recursive)  |

Insertion counts every shift and placement as a move; merge counts writes while merging, but not the final copy back. Searchers count one comparison and one probe per element examined. Recursion depth starts at 1. Quick sort skips empty ranges, but merge sort counts its initial call on an empty list and recursive binary search counts calls on empty ranges, including its final miss call.

Counts are exact and repeatable. Timings are noisy and depend on the machine, so they are not used for any claim. Data is generated from fixed seeds, so every run of the experiment gives the same numbers.

No global variables. State lives in objects that are passed in.

### The rules each class follows

- **`DataSet`**: a `dataclass`. Builds `random`, `sorted` and `reversed` lists from a seed. Knows nothing about algorithms.
- **`Counter`**: a plain class with counters and `reset()`. Knows nothing about algorithms either.
- **`Sorter`** (abstract): the public method `sort(values, counter)` **copies** the input, calls the subclass's `_sort`, checks the result is sorted, and returns it. The input list is never changed. This is the *template method* pattern: the base class owns the steps that must always happen, the child owns only the algorithm.
- **`BubbleSort`, `InsertionSort`, `SelectionSort`**: one file and one class each. They differ only in `_sort`.
- **`RecursiveSorter`** (abstract, child of `Sorter`): adds recursion-depth tracking via `_enter(counter, depth)`. `MergeSort` and `QuickSort` inherit from it, so they are children of a child.
  - `QuickSort` uses the **first element as the pivot** on purpose, so sorted input is its worst case and the nÂ² curve is visible. A docstring says so.
- **`Searcher`** (abstract): `search(sorted_values, target, counter)` returns the index, or `-1`. Same shape as `Sorter`.
- **`LinearSearch`, `BinarySearch`**: the iterative pair.
- **`RecursiveSearcher`** (abstract, child of `Searcher`), with **`RecursiveBinarySearch`** as its child. It must return the same index as `BinarySearch` for every input, and a test checks that.
- **`ExperimentManager`**: the only class that knows the whole system. It is given a list of sorters, a list of searchers, sizes, kinds and a seed count, and returns an `ExperimentResult` (a dataclass of rows). Sort rows average comparisons and moves across trials and record the maximum depth over those trials. Search uses the even-valued list 0, 2, ..., 2(n-1), with 200 alternating present and absent targets generated by an RNG seeded with n; absent targets are odd. It never draws or writes files.
- **`Plotter`**: takes an `ExperimentResult` and writes PNGs. It never runs experiments.

Dependencies point one way: `Plotter` and `ExperimentManager` use the algorithm classes; the algorithm classes use only `Counter`.

## The second lesson: how one agent prompts another

This repo's `sidecar/` folder is part of the display. Flo (the Foreman) wrote each prompt to Anna (the builder) before she built each piece, and Anna's `reports/` entry says what she did.
